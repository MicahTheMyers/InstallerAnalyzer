# .NET Framework 3.5 provisioning — 0.12.10 source increment, 2026-11-01

The shared Sandbox discovery/recording engine now includes a guest-only .NET 3.5 prerequisite step. It is triggered before installer launch by a managed CLR v2.0 installer (respecting a supplied CLR v4 runtime configuration) or an explicit .NET 3.5 MSI requirement description. During unattended candidate execution, newly observed tracked installer UI or the current MSI log can establish the requirement after a failed attempt. Mere DLL errors, unrelated runtime names, optional and negated requirements do not trigger it. Dynamic requirements that never appear in these supported evidence channels remain unrecognized; interactive native bootstrapper UI is not universally intercepted.

The step queries the feature state, verifies a real CLR 2.0/LINQ probe if already enabled, and otherwise runs one bounded DISM Enable-Feature /All /NoRestart attempt. The servicing process is limited to 180 seconds and updates the existing heartbeat. Feature queries and compiler/runtime probes have their own short limits. DISM exit zero, final Enabled state and successful real CLR execution are all required. A 3010 or pending state stops for a guest reboot. A failed/unknown/unverified state stops without installer retry, preserves diagnostics, and reports an environment prerequisite failure with a full-Windows-VM recommendation. It never services the host or reboots automatically. The unattended installer candidate gets at most one retry after verified provisioning; complete application lifecycle proof remains necessary for a pass/catalog entry.

Optional offline source: place matching official Microsoft NetFx3 source CABs in %LOCALAPPDATA%\InstallerAnalyzer\NetFx3Source before starting an analysis. At most eight matching CAB files, totaling at most 200 MB, are staged read-only into the guest. Windows DISM performs component-source validation. With that source present the command uses /LimitAccess /Source:C:\InstallerInput\NetFx3Source; otherwise DISM uses its normal Windows Update source. No Windows image/runtime download is added to production. On Windows build 28000+ the helper verifies an existing runtime or explicitly reports that Microsoft's standalone installer is required; it does not use the obsolete DISM path or automatically download/run the standalone package.

Structured evidence is retained in install-analysis.json, checkpoint JSON, netfx3-provisioning.json and the intelligence prerequisite report. Raw command/query/runtime logs use netfx3-*.txt in the existing diagnostic output. Failure classification displays the servicing exit code and VM/reboot guidance. The read-only AI snapshot can include the new evidence without gaining any write capabilities.

- 38 focused mocked PowerShell checks cover no-requirement/host guards, existing/missing/pending/unknown states, timeout/failure/reboot handling, verification failures, offline arguments, standalone-only builds, one successful installer retry and no retry after failure.
- 137 existing PowerShell checks rerun successfully; all 11 source script assemblies parse with the new helper wired in.
- Actual production helper in the owned full Windows 26100.1742 VM: feature reset to Disabled with Payload Removed, offline DISM exit 0, final Provisioned/RuntimeVerified=true, CLR=2.0.50727.9179. This is feature/runtime acceptance, not a dependent vendor installer lifecycle.
- Actual production helper in a fresh Sandbox: one DISM attempt exited 12006, RuntimeVerified/Provisioned=false, RequiresFullWindowsVM=true, explicit failure preserved, no installer retry. The Windows Sandbox servicing issue itself remains unresolved.
- Owned VM gracefully shut down, no Sandbox environments remain, and host NetFx3 remains DisabledWithPayloadRemoved. No UAC/security setting was changed by this implementation.
